# FobSim Research Experiment Workspace — Design

Date: 2026-11-05
Status: Draft for approval

## Intent

FobSim should become a reproducible research environment for blockchain researchers, not only a web form that launches the original CLI simulator. A researcher must be able to describe an experiment, run it without interfering with other users, preserve the exact inputs and outputs, reproduce it later, and download evidence suitable for further analysis or inclusion with a paper.

The first delivery focuses on the foundation required for trustworthy research:

1. isolated, authenticated simulation jobs;
2. research projects and experiments;
3. reproducible run metadata;
4. durable run details and research exports.

Batch parameter sweeps and statistical analysis are deliberately deferred until individual runs are isolated and reproducible.

## Users and primary workflow

The primary user is a blockchain researcher working alone. Team collaboration and public sharing are future work.

The main workflow is:

1. Create a research project with a name and description.
2. Create an experiment inside the project with a name, hypothesis, simulation choices, configuration, and random seed.
3. Start a run. The API creates an immutable configuration snapshot and places the run in a FIFO queue.
4. Observe queued/running/completed/failed/stopped status and live logs for that run only.
5. Open a run detail page to inspect its inputs, environment, metrics, logs, and raw results.
6. Clone the experiment or rerun it with the same seed.
7. Export a reproducibility bundle containing machine-readable metadata, measurements, logs, and raw results.

## Goals

- No user can read, stop, or alter another user's runs.
- Every run has its own working directory, configuration file, logs, and result files.
- Starting one run never overwrites another run's configuration or artifacts.
- The same configuration and random seed can be rerun intentionally.
- Run metadata and core outputs survive a backend restart and Render's ephemeral filesystem.
- Existing simulation history is retained.
- The current consensus algorithms and blockchain functions continue to work.
- The API and UI expose explicit failure states instead of reporting stopped or completed for every outcome.

## Non-goals for this delivery

- Parallel execution across multiple servers or regions.
- Parameter sweeps, Monte Carlo orchestration, confidence intervals, or significance tests.
- Shared team workspaces, comments, public links, or role-based access.
- PDF report generation.
- Permanent S3-compatible object storage.
- New consensus algorithms, attacks, or network models.
- Rewriting the original simulation engine into a new framework.

## Existing problems addressed

The current backend keeps `simulation_running`, `simulation_output`, and `simulation_process` as process-wide globals. The configuration endpoints write a shared `Sim_parameters.json`, while results are read from a shared `temporary` directory. Status, stop, config, and result endpoints are not consistently protected or scoped to a user. This creates cross-user interference and makes a run impossible to reproduce reliably.

The current history record stores summary metrics but does not provide a complete run detail resource. The frontend's history action has no detail destination, and an experiment cannot be cloned or exported.

## Domain model

### ResearchProject

- `id`: UUID
- `user_id`: owner
- `name`: required, 1–120 characters
- `description`: optional text
- `deleted_at`: nullable soft-delete timestamp
- `created_at`, `updated_at`

Only the owner can list, read, update, or delete the project. Deleting a project is rejected while it has active runs. Otherwise deletion is soft-delete in this phase so research records are not accidentally lost.

### Experiment

- `id`: UUID
- `project_id`
- `name`: required, 1–160 characters
- `hypothesis`: optional text
- `notes`: optional text
- `blockchain_function`
- `blockchain_placement`
- `consensus_algorithm`
- `config`: validated JSON snapshot template
- `default_seed`: integer generated by the server when omitted
- `archived_at`: nullable soft-archive timestamp
- `created_at`, `updated_at`

Editing an experiment changes only its template. Existing runs remain immutable.

### SimulationRun

The existing `simulations` table is evolved rather than replaced so historical data remains available.

New fields:

- `public_id`: UUID used in URLs and APIs
- `experiment_id`: nullable for legacy rows
- `seed`
- `engine_version`: current Git commit when available, otherwise application version
- `status`: `queued`, `running`, `completed`, `failed`, `stopped`, or `interrupted`
- `error_message`: nullable and safe for display
- `config`: immutable full configuration snapshot
- `queued_at`, `started_at`, `ended_at`
- `logs_text`: bounded persisted log output
- `results_json`: structured raw result summary
- `artifact_manifest`: filenames, media types, byte sizes, and SHA-256 checksums

The existing metrics remain: blocks, CPU, forks, consistency, latency, throughput, and estimated energy.

Legacy simulation rows keep a nullable `experiment_id` and appear under an automatically presented “Legacy history” section. No destructive data migration is required.

## Persistence and migrations

Alembic is introduced for explicit PostgreSQL schema migrations. Application startup must no longer rely on `Base.metadata.create_all()` as the only schema-management mechanism.

The production database predates Alembic. The initial migration therefore inspects and adopts the existing tables safely instead of attempting to recreate them. It then creates the new tables/columns, backfills unique public UUIDs, maps legacy statuses, and changes leftover `running` rows to `interrupted`. The backend container runs `alembic upgrade head` before starting Uvicorn and starts the API only after migration succeeds. Production startup removes the `create_all()` schema-management path.

PostgreSQL is the durable store for phase one. Configuration, metadata, logs, metrics, and bounded structured results are stored in the database. This avoids losing research evidence when Render replaces its ephemeral filesystem.

Limits:

- persisted logs: maximum 2 MiB per run;
- persisted structured raw results: maximum 5 MiB per run;
- output beyond the limit is marked truncated in the manifest;
- temporary working directories are deleted after persistence and export collection.

A storage interface is introduced so a future S3-compatible artifact store can replace the database limits without changing API contracts. External object storage is not required in this delivery.

Logs are captured with a monotonic line cursor and bounded while the run is active, not only at completion. When the 2 MiB UTF-8 limit is reached, the oldest complete lines are removed. Log responses include `next_cursor` and `truncated_before_cursor` so polling clients can detect a gap.

`results_json` uses a versioned schema containing public block data, stakes, burned-coin summaries, and calculation metadata. Private keys, `.env` files, credentials, password data, and other temporary secrets are never persisted or exported. Manifest checksums are SHA-256 values calculated over the exact final bytes of each ZIP entry.

## Job execution and isolation

### Queue

The backend owns a single FIFO queue and one simulation worker. Multiple users may enqueue jobs, but runs execute sequentially in this phase. The legacy engine uses fixed socket ports and is therefore not safe for parallel subprocesses even when file workspaces are isolated. Dynamic port allocation is deferred.

Queue state is represented in PostgreSQL. On startup, runs previously marked `queued` are re-enqueued; runs left as `running` are marked `interrupted`, because their subprocess cannot survive a service restart.

Claiming a queued run is atomic and uses a database transaction with row locking. Startup recovery and the worker use the same claim operation so a lifecycle hook running twice cannot execute one run twice.

This design supports one backend instance running one Uvicorn worker. Distributed workers, multiple API replicas, and parallel simulations are explicitly unsupported until both dynamic port allocation and a distributed queue such as Redis/RQ, Celery, or a managed job service are introduced. Deployment configuration must enforce the single-worker constraint.

### Per-run workspace

Each run receives a newly created temporary directory. The backend copies the required engine source files into it, writes that run's `Sim_parameters.json`, creates an isolated `temporary` output directory, and launches `main.py` with that directory as its working directory.

The workspace is created from an explicit allowlist: required engine Python modules, `messages_formats/`, the generated configuration, and necessary non-secret data files. It never copies `api/`, Git metadata, `.env` files, credentials, or unrelated repository files.

This avoids a risky rewrite of every engine file that currently assumes relative paths. It also prevents one run from reading another run's chains, wallets, stakes, or burned-coin files.

The subprocess environment includes:

- `FOBSIM_RUN_ID`
- `FOBSIM_RANDOM_SEED`
- `PYTHONHASHSEED`

The seed is a signed 64-bit integer generated with a cryptographically secure generator when omitted. The engine initializes Python's random generator from `FOBSIM_RANDOM_SEED` before network construction. Any future NumPy-based randomness must use the same run seed. Reproducibility means preserving inputs and reproducing seeded pseudo-random choices; wall-clock timestamps, CPU readings, cryptographic material, and full byte-for-byte output are not promised to be identical.

`engine_version` uses `RENDER_GIT_COMMIT` when available, then an application-version environment variable, and finally `unknown`.

### Ownership and cancellation

The in-memory process registry is keyed by run UUID, not by one global process. A stop request first loads the run through an owner-scoped database query. A queued run can be changed directly to `stopped`; a running process owned by the authenticated user can be terminated. Stop requests for terminal states return `409 Conflict`.

The backend persists each status transition. A failed subprocess stores its return code and a sanitized error summary.

## API design

All endpoints below require bearer authentication.

Projects:

- `POST /api/projects`
- `GET /api/projects`
- `GET /api/projects/{project_id}`
- `PATCH /api/projects/{project_id}`
- `DELETE /api/projects/{project_id}` (soft delete)

Experiments:

- `POST /api/projects/{project_id}/experiments`
- `GET /api/projects/{project_id}/experiments`
- `GET /api/experiments/{experiment_id}`
- `PATCH /api/experiments/{experiment_id}`
- `DELETE /api/experiments/{experiment_id}` (soft archive)
- `POST /api/experiments/{experiment_id}/clone`

Runs:

- `POST /api/experiments/{experiment_id}/runs` returns `202 Accepted`
- `GET /api/runs?project_id=&experiment_id=&status=&cursor=&limit=`
- `GET /api/runs/{run_id}`
- `GET /api/runs/{run_id}/logs?after=<cursor>`
- `POST /api/runs/{run_id}/stop`
- `POST /api/runs/{run_id}/rerun`
- `GET /api/runs/{run_id}/export?format=json|csv|zip`

The existing `/api/run`, `/api/status`, `/api/stop`, `/api/results`, and `/api/simulations` routes remain temporarily as authenticated compatibility adapters during the frontend migration. `/api/simulations` delegates to the new paginated run query. No compatibility endpoint may read process-wide global state.

`GET /api/config` becomes an authenticated endpoint that returns immutable canonical defaults. `POST /api/config` is removed because experiments own configuration. The global `/ws/output` route is removed; live output uses the owner-scoped run log endpoint. A future run-scoped WebSocket may be added without changing the run model.

All list endpoints are paginated from their first release. Pydantic request and response models are explicit; untyped `List[dict]` responses are removed.

Configuration uses one canonical schema and a central mapping to legacy `Sim_parameters.json` keys, including existing question-mark-suffixed keys. Every run snapshot contains the complete effective configuration, not only fields currently displayed in the UI.

Validation includes safe numeric bounds and placement-aware cross-field rules. With Fog placement, effective miner count is `NumOfFogNodes`; otherwise it is `NumOfMiners`. Byzantine count, neighbour count, and DPoS delegates cannot exceed the effective miner count.

## Export bundle

The ZIP reproducibility bundle contains:

- `manifest.json`: schema version, project, experiment, run ID, timestamps, seed, engine version, status, checksums, and truncation flags;
- `config.json`: exact immutable run configuration;
- `metrics.csv`: one row of summary measurements with units;
- `logs.txt`: persisted simulation log;
- `results.json`: structured chain/stake/burned-coin summary retained by the run;
- `README.txt`: short reproduction instructions and FobSim citation information.

JSON export returns the manifest, config, metrics, and results as one document. CSV export returns the metrics table. Exports are generated on demand and do not need permanent files.

CSV columns include explicit units. For legacy runs without a seed, logs, or structured results, Run Detail presents a clearly marked partial record. It does not invent missing data; unavailable exports or fields explain why they cannot be produced.

## Frontend experience

### Projects

The main dashboard gains a Projects section showing project name, experiment count, latest run, and last updated time. A researcher can create and edit a project.

### Experiment editor

The current four-step simulator becomes an experiment editor. Before technical parameters, it collects experiment name and optional hypothesis. The existing function, consensus, placement, and parameter controls are reused.

Saving creates or updates the experiment template. “Run experiment” creates a new immutable run; it no longer writes a shared global server configuration.

### Run detail

`/runs/{run_id}` displays:

- status and queue/running progress;
- project and experiment context;
- configuration and random seed;
- live or persisted logs;
- summary metric cards;
- raw result availability and truncation warnings;
- Stop, Rerun, Clone Experiment, and Export actions.

History links to this page. Analytics continues to aggregate completed runs owned by the current user, but it reads only immutable run records.

Soft-deleted projects and archived experiments are hidden from normal lists, while their historical run detail and exports remain accessible to the owner.

## Security and integrity

- Every project, experiment, run, log, stop, result, and export query is owner-scoped.
- CORS uses an environment-configured frontend origin instead of `*`.
- JWT validation remains the authentication mechanism for this phase.
- Input bounds prevent configurations that can exhaust the free Render service accidentally.
- Export filenames are fixed by the server; user input is never used as a filesystem path.
- Temporary directories use system-generated paths and are always cleaned up.
- Logs and error messages do not include environment variables, API keys, database URLs, or password data.
- Checksums allow researchers to confirm that an exported artifact has not changed.

## Failure and recovery behavior

- Invalid experiments are rejected before creating a run.
- A queued run can be stopped and becomes `stopped` without launching a subprocess.
- A running run becomes `failed` on non-zero process exit and retains logs.
- A backend restart marks orphaned running jobs `interrupted` and safely resumes queued jobs.
- Persistence failure leaves the run `failed` and records a safe error where possible.
- If results exceed persistence limits, the run may still complete, but the manifest clearly reports truncation.

Allowed status transitions are:

- `queued → running | stopped`
- `running → completed | failed | stopped | interrupted`

Terminal states are immutable. Rerun always creates a new queued run and never reopens or mutates the original.

## Testing and acceptance criteria

Backend tests must prove:

- project/experiment/run ownership cannot be bypassed;
- two users can enqueue runs without sharing config, logs, result files, or stop controls;
- the same config and seed produce the same deterministic engine choices covered by tests;
- queued, running, stopped, failed, interrupted, and completed transitions are valid;
- restart recovery marks orphaned jobs and requeues queued jobs;
- export manifests contain the expected seed, engine version, config, units, and checksums;
- configuration bounds and cross-field validation work;
- legacy simulation rows remain readable.

Queue tests must also prove atomic claiming: repeated startup/worker hooks cannot launch the same queued run twice.

Frontend tests must cover project creation, experiment saving, run launch, queued/running/completed states, owner-safe error states, run details, rerun, and export controls.

Acceptance criteria:

1. Two authenticated test users can create and run different experiments without observing or modifying each other's data.
2. No request writes the repository's shared `Sim_parameters.json` in production execution.
3. Every completed run has immutable config, seed, engine version, timestamps, metrics, logs, and a manifest.
4. A run can be rerun with the same config and seed.
5. JSON, CSV, and ZIP exports download successfully and contain documented units.
6. Existing history remains visible after migration.
7. Backend tests, frontend tests, lint, and production build pass.
8. Legacy run details clearly label unavailable seed/log/result fields and do not generate misleading complete bundles.

## Delivery sequence

1. Milestone 1: Alembic baseline, new models, ownership APIs, canonical configuration, and legacy migration.
2. Milestone 2: isolated single-worker queue, seed handling, lifecycle persistence, recovery, and compatibility adapters.
3. Milestone 3: Projects, Experiment Editor, Run Detail, history migration, and owner-scoped log polling.
4. Milestone 4: JSON/CSV/ZIP exports, cleanup, analytics migration, removal of global endpoints/state, CORS hardening, and production verification.

Each milestone is independently tested, deployable, and backward-compatible with the preceding milestone.

## Decisions made in this design

- PostgreSQL stores bounded artifacts in phase one to avoid requiring new infrastructure.
- Production concurrency defaults to one but jobs are independently queued and owned.
- Per-run source workspaces isolate the legacy CLI engine without a full rewrite.
- Existing simulation rows are preserved as legacy history.
- Exports are JSON, CSV, and ZIP; PDF is deferred.
- Collaboration, batch analysis, advanced statistics, and new simulation science are deferred until the research foundation is reliable.
- UUIDs are server-generated, unique, non-null, and backfilled for legacy runs.
- All persisted timestamps are timezone-aware UTC values.
- `queued` and `running` are the active statuses that prevent project deletion.
- Analytics aggregates only completed runs owned by the authenticated user.
